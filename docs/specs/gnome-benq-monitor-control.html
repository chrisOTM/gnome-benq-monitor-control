gnome-benq-monitor-control — Design Spec

Status: implemented (v0.1.0) · Date: 2026-10-19 · Author: chrisOTM (with Claude) · Port of linux-desktop/benq-monitor-control v0.1.0 (KDE tray app, PySide6/QML)

1. Purpose

The KDE tray app does not work on GNOME: there is no system tray, and its quick panel relies on wlr-layer-shell, which Mutter does not implement (see the parked note benq-monitor-control/docs/issues/gnome-support.md). This project brings the same control of the BenQ MA320U to GNOME Shell 50 (Ubuntu 26.04) as a native GNOME Shell extension.

3. Architecture

Pure GJS, no Python or helper daemon. ddcutil is started with Gio.Subprocess asynchronously, so the shell never blocks on the I²C bus.

ModuleResponsibilityShell imports
lib/model.jsMA320U description: VCP codes, choices, locks.no
lib/ddcutil.jsParsers for terse output, error classification, async runner with 10 s timeout and one retry.no (Gio)
lib/session.jsMonitor state, serialized job queue (one ddcutil call at a time), verified writes, learned locks, latest-value-wins coalescing for sliders.no
lib/sun.js, lib/scheduler.js, lib/scenario.jsNOAA sun times, active/next scenario, JSON validation (same format as the KDE app).no
lib/flow.jsScenario activation, 60 s tick, clock-jump detection, retry after reconnect.no (GLib)
lib/i18n.jsLookup table translations (EN source strings, DE table).no
ui/indicator.jsTop-bar button and menu.yes
extension.jsWiring: settings, monitor hotplug, resume, lock screen, notifications.yes
prefs.jsAdw preferences.no (Gtk/Adw)

Everything under lib/ runs under plain gjs, so it is unit-tested with gjs -m tests/run.js.

4. Behaviour differences to the KDE app

  • Polling: values are read when the menu opens and then every sync interval seconds while it stays open. No background polling while closed (the KDE app polled every 5 s permanently).
  • Reconnect: on monitors-changed (hotplug, input switched back), 3 s and 10 s later, and every 60 s while unreachable (the KDE app retried every 10 s; ddcutil detect probes every bus, which is wasteful on battery).
  • Lock screen: session modes user and unlock-dialog, so scheduled scenarios still fire while the screen is locked; the indicator is hidden while locked.
  • Brightness keys: the extension takes over GNOME's four screen brightness keybindings (screen-brightness-up/down and the -monitor variants; the cycle keys stay untouched) with the same schema, flags and Shell.ActionMode.ALL, so they keep working on the lock screen. GNOME's original handler (from Main.brightnessManager) runs first and steps the laptop panel if one is active. Then the monitor's brightness (VCP 0x10) moves by 1/20 of its maximum (5 for 0–100), clamped, based on the latest target (pending or shown value), so a held key coalesces into one pending write. Fn + key steps every screen; Shift + Fn + key steps the monitor only if the logical monitor under the pointer contains its connector (ddcutil detect reports card1-DP-1, Meta calls it DP-1), otherwise it is pure delegation to GNOME. One combined OSD call shows GNOME's scales plus the monitor's new level immediately. If the monitor is unreachable or brightness is locked (HDR), only GNOME acts; if the connector is unknown, the global keys still step the monitor but without an OSD level. Disabling the extension or the setting restores GNOME's handlers; if Main.brightnessManager or its methods are missing, the keybindings are not touched.
  • Activate now exists only in the menu, not in the preferences (prefs run in a separate process).

6. Safety

Unchanged from the KDE app: only the six VCP codes 0xDC, 0x10, 0x62, 0x60, 0x19, 0x81 are written, every write except input is verified by ddcutil's read-back, input switches need confirmation.
