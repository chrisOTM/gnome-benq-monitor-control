gnome-benq-monitor-control — Design Spec

Status: implemented (v0.2.0) · Date: 2026-11-11 · Author: chrisOTM (with Claude) · Port of _archive/benq-monitor-control v0.1.0 (KDE tray app, PySide6/QML); v0.2.0 follows that app's v0.2.0 audit fixes

1. Purpose

The KDE tray app does not work on GNOME: there is no system tray, and its quick panel relies on wlr-layer-shell, which Mutter does not implement (see the parked note benq-monitor-control/docs/issues/gnome-support.md). This project brings the same control of the BenQ MA320U to GNOME Shell 50 (Ubuntu 26.04) as a native GNOME Shell extension.

3. Architecture

Pure GJS, no Python or helper daemon. ddcutil is started with Gio.Subprocess asynchronously, so the shell never blocks on the I²C bus.

ModuleResponsibilityShell imports
lib/model.jsMA320U description: VCP codes, choices, locks.no

lib/session.jsMonitor state, serialized job queue (one ddcutil call at a time), verified writes, learned locks (two rejections in a row, expire after 10 minutes), latest-value-wins coalescing for sliders, fresh read before relative steps.no

Everything under lib/ runs under plain gjs, so it is unit-tested with gjs -m tests/run.js.

4. Behaviour differences to the KDE app

  • Polling: values are read when the menu opens and then every sync interval seconds while it stays open. No background polling while closed (the KDE app polled every 5 s permanently).
  • Reconnect: on monitors-changed (hotplug, input switched back), 3 s and 10 s later, and every 60 s while unreachable, but only while a screen other than the laptop's built-in panel is connected (the KDE app retried every 10 s; ddcutil detect probes every bus, which is wasteful on battery). On the laptop alone nothing talks to the bus. With the monitor attached the only background traffic is one short read per minute while the input guard holds a scenario, and one read before a brightness key step.
  • Rejected writes: after a rejection the session re-reads all values. If the value arrived anyway, it counts as applied. A control is locked only after the second rejection in a row; a learned lock is forgotten after 10 minutes, when the menu opens, or on Detect again. Static locks (Low Blue Light in sRGB and Display P3, HDR) are unchanged.
  • Input guard: the MA320U keeps answering DDC/CI while it shows another computer. Scheduled scenarios (scheduled start, re-apply after login, resume or clock jump, retries) and the brightness keys therefore act only while a fresh read shows this computer's input. A held scenario shows FloW paused — the monitor shows another input in the menu header, is re-checked every minute and applied silently (no applications, no notification) when the input returns. Picking a scenario in the menu and all menu controls always work. This computer's input is learned at first contact, but only if it fits the connector the monitor is found on (USB-C arrives as DisplayPort, so on a DisplayPort connector only USB-C is learned). It can be changed, reset or the guard switched off under General.
  • FloW semantics: a scenario picked in the menu stays in effect until the next scheduled start, also across resume and clock jumps. One re-apply per resume. At most three attempts per trigger while the monitor does not answer; a new trigger starts over. No notification when nothing reached the monitor. The offset applies to sunrise and sunset only. Disabling the extension cancels a running ddcutil command and drops queued writes.
  • Input switch: the confirmation says the monitor will show another device. The extension keeps its connection, the menu shows the new input and can switch back.
  • Lock screen: session modes user and unlock-dialog, so scheduled scenarios still fire while the screen is locked; the indicator is hidden while locked.
  • Brightness keys: the extension takes over GNOME's four screen brightness keybindings (screen-brightness-up/down and the -monitor variants; the cycle keys stay untouched) with the same schema, flags and Shell.ActionMode.ALL, so they keep working on the lock screen. GNOME's original handler (from Main.brightnessManager) runs first and steps the laptop panel if one is active. Then the monitor's brightness (VCP 0x10) moves by 1/20 of its maximum (5 for 0–100), clamped, based on the latest target (pending or shown value), so a held key coalesces into one pending write. If the last read or write is older than 10 seconds, the current values are read first, so a press steps from the real brightness even if the monitor's own buttons or Brightness Intelligence changed it. While the monitor shows another computer (input guard) the keys do not touch the monitor; GNOME's handler still runs. Fn + key steps every screen; Shift + Fn + key steps the monitor only if the logical monitor under the pointer contains its connector (ddcutil detect reports card1-DP-1, Meta calls it DP-1), otherwise it is pure delegation to GNOME. One combined OSD call shows GNOME's scales plus the monitor's new level immediately. If the monitor is unreachable or brightness is locked (HDR), only GNOME acts; if the connector is unknown, the global keys still step the monitor but without an OSD level. Disabling the extension or the setting restores GNOME's handlers; if Main.brightnessManager or its methods are missing, the keybindings are not touched.
  • Activate now exists only in the menu, not in the preferences (prefs run in a separate process).

6. Safety

Unchanged from the KDE app: only the six VCP codes 0xDC, 0x10, 0x62, 0x60, 0x19, 0x81 are written, every write except input is verified by ddcutil's read-back (--verify is passed explicitly), input switches need confirmation. A range value is never written without a known maximum: brightness is pinned to 100, Low Blue Light to 5, volume uses the maximum the monitor reports.

Preferences keep invalid scenario entries in the stored JSON when they save; an open_app desktop id must be a plain file name.
